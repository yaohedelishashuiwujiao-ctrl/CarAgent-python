# 大规模 PDF 结构化切片实测报告

日期：2026-07-19

## 结论

这次不是用少量文档推算，而是对汽车相关语料执行了完整冷处理。输入清单包含 1,007 份已下载 PDF，成功解析 1,006 份、失败 1 份，共处理 16,426 页和 48,339,540 个去空白字符，最终生成 49,082 个可追溯切片。

该实现可以替代项目原先的固定字符切片，作为离线建库管线的第一版。它已经解决页眉页脚、章节边界、表格文本、页码追踪、父级章节、硬长度限制、质量检测、失败隔离和增量缓存，但还不能被描述成“完整企业级文档理解平台”。

## 数据集边界

- 来源：汽车、自动驾驶、车辆工程相关 arXiv PDF 清单。
- 本轮进入切片管线：1,007 份。
- 成功：1,006 份。
- 失败：1 份，`arxiv-2411.15007v1`，Poppler 报错 `Couldn't read xref table`，说明文件交叉引用表损坏。
- 语料以英文、文本型学术 PDF 为主，不代表扫描件、企业手册、复杂中文研报和 PPT 的混合生产分布。

因此，这组数据可以证明吞吐、缓存、边界控制和故障隔离，不能单独证明 OCR、复杂表格还原或最终问答准确率。

## 切片策略

处理链路如下：

1. 使用 Poppler layout 模式逐页抽取文本，保留换页符和横向空格。
2. 统计每页顶部和底部候选行，删除跨页重复的页眉、页脚和归一化页码。
3. 识别编号标题、常见章节标题和全大写短标题，维护章节路径。
4. 对同时具备列对齐和重复数值单元格的块标记为表格，减少双栏论文被误判为表格。
5. 以章节和块为边界进行动态装箱：目标 1,200 字符，硬上限 1,800 字符，语义尾部重叠 180 字符。
6. 每个切片保存稳定 `chunk_id`、章节级 `parent_id`、页码范围、章节路径和内容类型。
7. 根据内容 SHA-256、解析器版本和配置建立文档级缓存；单文档失败不会中断批任务。
8. 文本密度低于阈值的文档标记为 `needs_ocr`，交给后续 OCR 队列。本轮成功文档均为文本型 PDF，因此该值为 0。

## 质量修正记录

第一版表格规则只要发现大间距列就判为表格，在双栏学术 PDF 上导致 28,397 / 64,702 个切片带表格标签（43.9%），明显过高。第二版要求“列对齐 + 重复数值单元格”同时成立，表格标签降至 20.9%。

统计第二版结果时还发现 3 个切片因极端横向空格超过 1,800 字符，最大为 3,992。第三版对异常长表格行进行硬切分，并限制重复表头的长度，最终超限数降为 0。这个过程比只展示一个漂亮的最终数字更能说明评估确实发现并推动了实现修正。

## 尚未完成的部分

- 当前只产生 `needs_ocr` 路由信号，没有集成 OCR 引擎和版面模型。
- 表格保留了行列空格和表头，不等同于还原为严格 HTML/二维单元格。
- `parent_id` 指向章节级逻辑父节点，但尚未另建可检索的 parent 摘要索引。
- 尚未把这 49,082 个切片接入在线混合检索；现有在线 `RagService` 仍是小语料固定字符切片。
- 尚未基于人工标注问题集测 Recall@K、MRR、答案忠实度和引用准确率，因此不能声称 RAG 准确率已经达到某个高数值。

## 面试表述建议

> 我们原来的 RAG 只按固定字符切分，文档规模上来后会切断章节和表格，也无法定位原页。我把它改成了离线、可恢复的结构化管线：先逐页抽取并去除重复页眉页脚，再识别章节和表格块，按 1,200 字符目标、1,800 硬上限和 180 字符重叠生成子切片，同时保存章节父节点、页码和稳定 ID。缓存按文件哈希和解析器版本失效，坏文件单独隔离，低文本密度文件进入 OCR 队列。
>
> 我在 1,007 份汽车相关 PDF 上做了全量实测，成功处理 1,006 份、16,426 页、约 4,834 万字符，产出 49,082 个切片。切片 P95 为 1,790 字符，没有空切片或超长切片；冷处理约 26.3 秒，缓存重跑约 0.58 秒。评估过程中还发现双栏论文会导致表格误判，以及极端排版会突破长度上限，我分别收紧联合判定条件和增加硬切分修正了它们。
>
> 这组实验验证的是文档处理能力，不是 RAG 最终准确率。下一步还要接入混合检索和 rerank，并用人工标注问题集测 Recall@K、MRR 和引用准确率。我不会用少量文档上的高分去包装生产效果。
