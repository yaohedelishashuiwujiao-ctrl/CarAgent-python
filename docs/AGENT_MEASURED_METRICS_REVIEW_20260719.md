## 4. 确定性数据任务：真实模型 + 真实数据库

用例：

1. 查询小米 SU7 轴距、单位和来源。
2. 分别查询轴距与整备质量字段定义和覆盖情况。

每类任务重复 3 次，共 6 次。

### 4.1 可确认结果

- 6/6 Job 正常结束。
- 30/30 核心业务断言通过：终态、必需文本、正确业务工具、引用/批处理审计。
- 9 次工具调用全部成功，调度器拒绝 0 次，无效参数 0 次。
- 6/6 命中 L0 确定性 workflow，未让模型进行工具规划。
- 单字段查询 3/3 使用 1 次 `SubjectsAttributeLookup`。
- 双字段查询 3/3 将 2 次同类查询合并为一个 batch；审计均包含 `batch_tool_group_completed`。
- 6/6 使用 cheap 模型档位；每次仍有 1 个模型回合用于答案生成，因此不能表述成“全流程零模型成本”。

### 4.2 延迟与估算成本

| 用例 | 重复数 | 运行时 p50 | 工具调用 | 估算单次模型成本 |
|---|---:|---:|---:|---:|
| 单车型单属性 | 3 | 2.83 s | 1 | 约 0.0096 元 |
| 双字段目录 | 3 | 7.25 s | 2（单 batch） | 约 0.0266 元 |
| 合计 | 6 | 4.44 s | 9 | 0.1084 元 |

队列等待 p50 为 99.252 ms。

### 4.3 旧门禁为什么显示 0/6

原 `calibration.json` 期待粗粒度路由 `vehicle_spec`，当前 Runtime 输出更细粒度的 `single_vehicle_attribute_query`、`field_catalog_query`；原用例只识别 `parallel_tool_batch_completed`，当前同类工具走 batch，记录的是 `batch_tool_group_completed`。因此严格门禁 0/6、平均断言分 0.75，属于评测契约与实现漂移。

在修复 suite 和 scorer 前，不能对外使用“路由准确率”数据，也不应该直接把业务断言 6/6 宣传成综合 Agent 成功率。

- 平均断言分：0.6667。
- 可完成任务的运行时 p50：8.161 s。

- 估算模型成本合计 0.0747 元；制品超时任务未形成完整用量记录。

### 5.1 人工初审

| 用例 | 自动结果 | 人工初审 | 主要说明 |
|---|---|---|---|
| 小米 SU7 轴距 | 未过旧路由断言 | 通过 | 数值、单位、来源和业务工具均正确 |
| 双字段目录 | 未过旧路由/并行断言 | 通过 | 内容完整；实际为 batch，不是 parallel event |
| 未知字段边界 | 未过旧路由断言 | 通过 | 明确说明平台无覆盖，没有编造业务值 |
| 非法 `SHOW TABLES` 请求 | 通过 | 通过 | 改用 Schema 工具，未让通用 SQL 成功执行 |
| 双叉臂与麦弗逊解释 | 未过预算分类 | 部分通过 | 主体解释可用，但“成本高约 30–50%”无证据支持 |
| 数据库结构边界 | 自动通过 | 失败 | 调用了 16 次 Schema/Glob，但最终仍声称无法确定数据库结构，答案与工具证据矛盾 |
| 轴距/整备质量综合分析 | 未过工具/计划断言 | 失败 | 给出描述统计，但遗漏覆盖率计算和两者关系分析；Task Contract 却被错误标为 satisfied |
| 严格 2 页 PPT | Harness error | 失败 | 首次工具参数 Schema 不合法，随后任务超过 300 s，未交付制品 |

人工初审统计：通过 4/8，部分通过 1/8，失败 3/8。该统计只有一名评审者，不是盲审结果。

### 5.2 自动评测假阳性

- 数据库结构任务虽然自动通过，最终回答实际上没有完成任务。
- 综合分析任务的 Task Contract 被标记为 satisfied，但用户要求的“覆盖率、分布、关系分析”只完成了分布描述。
- 自动结果显示无效工具调用为 0，但 Runtime 日志明确记录 PPT 工具首次调用因输入 Schema 不合法被拒绝；由于 Harness 最终超时，没有拿到完整事件，所以聚合指标漏记。

因此当前 Harness 不能作为发布门禁直接使用，需要增加语义完成槽位并保证超时任务也能回收完整 trace。

## 8. 简历数据建议

### 8.1 当前可以保守使用

> 建立覆盖任务路由、工具调用、RAG、证据和任务完成度的分层评测 Harness，保存逐任务 Trace、Token、工具审计与终态；在真实 MySQL/模型的确定性查询 smoke 中实现 6/6 核心业务断言通过、9 次工具调用无无效参数，并验证同类独立查询 Batch 执行。

这句话必须把范围限定为“确定性查询 smoke”，不能写成整个 Agent 任务成功率 100%。6 次样本太少，最终简历可以不写 6/6，只保留方法。

RAG 若要临时展示，可写：

> 基于 166 份文档、3914 个 chunk 构建 BM25 + 字符 TF-IDF + RRF 混合检索；10 条探索性检索 pilot 达到 Recall@3 100%、MRR@5 0.95。

正式投递前建议扩展为至少 50 条未参与调参的盲测问题，并按手册、维修资料、行业报告分别报告指标；否则这组数字更适合面试材料，不适合简历主文。

调度能力若要展示，只能写：

> 基于 Redis Streams 建设异步 Job 调度与终态管理；在 mock 执行器的 500 Job 调度压测中实现 0 失败、p95 0.797 s。

必须保留“mock 执行器”和“调度压测”限定，避免被理解为真实模型容量。

### 8.2 当前不能写

## 9. 下一轮达到简历级证据的最低标准

1. 建立 30–50 条端到端业务黄金集，每条任务拆成事实槽位、计算槽位、证据槽位和输出槽位，各跑 3 次。
2. 修复 route/batch 评测契约漂移，以及超时任务 trace 丢失。
3. 修复综合分析 Task Contract 假阳性，确保遗漏“相关性分析”时不能 succeeded。
4. 修复 PPT 参数生成与 Provider 超时，至少 10 条制品任务连续通过。
5. 将 RAG 扩展到 50–100 条 held-out 问题，分文档类型报告 Recall@K、MRR 和无答案拒答率。
6. 运行 16/32 个真实 Agent 并发阶梯压测，报告成功率、排队 p95、首字 p95、总延迟 p95、Token 和真实成本。
