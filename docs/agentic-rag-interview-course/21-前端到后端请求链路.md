# 21-前端到后端请求链路

## 这一层解决什么问题

如果只讲 `run_agent_loop()`，项目会像一个命令行 Agent demo。真实项目是全栈系统：用户从前端发起请求，后端创建异步 Agent Job，Runtime 执行多轮模型和工具，前端通过 SSE 接收过程和最终结果。

这一层回答的是：用户的一次 Agent 请求怎么从 Web 页面进入完整系统。

这里的工程重点是：Agent 请求不是普通短 HTTP 查询。

一次复杂 Agent 任务可能持续几十秒甚至更久，中间包含：

- 多轮模型调用。
- 多个 RAG/SQL/Web 工具。
- 图表或 PPT 产物生成。
- fallback、citation repair、context compact。

如果前端直接同步调用 Runtime，会遇到超时、无法排队、无法恢复、无法观测的问题。所以全栈链路必须把“用户请求”和“Agent 执行”解耦。

## 最小模式

```mermaid
flowchart TD
    UI[Frontend Agent Page] --> API[POST /api/agent/chat_jobs]
    API --> AUTH[Principal / data_scope / allowed_tools]
    AUTH --> JOB[AgentJobService.create_job]
    JOB --> QUEUE[Job Queue]
    QUEUE --> WORKER[Worker / Runtime Proxy]
    WORKER --> RUNTIME[Agent Runtime /api/chat_stream]
    RUNTIME --> EVENTS[Agent Events]
    EVENTS --> SSE[GET /api/agent/chat_jobs/{job_id}/events]
    SSE --> UI
```

## 加上这一层后 Loop 怎么变化

没有后端 Job：

```text
前端 -> 同步请求 -> 等模型和工具全部完成 -> 返回
```

问题：

- 长任务容易 HTTP 超时
- 不能排队
- 不能取消
- 不能恢复
- 不好做多用户公平调度
- 不好持久化事件和审计

有后端 Job：

```text
前端创建 job
后端立即返回 job_id/status_url/events_url
前端订阅 SSE
后端异步调度和执行
```

这个设计把一次 Agent 请求拆成两个阶段：

| 阶段 | 目标 |
|---|---|
| 创建 Job | 快速返回 job_id，固化权限、路由、幂等键 |
| 异步执行 | 后端调度 worker，Runtime 多轮执行，事件流回前端 |

这样前端不需要持有一个长时间阻塞请求，后端也能做排队、公平调度、重试和事件持久化。

## 我们项目里的真实源码

后端入口：

- `backend/app/main.py`
- `backend/app/routers/agent_jobs.py`
- `backend/app/services/agent_jobs.py`
- `backend/app/services/agent_routing.py`

前端入口：

- `frontend/src/App.tsx`
- `frontend/src/api.ts`
- `frontend/src/pages/AgentPage.tsx`

后端注册路由：

```python
app.include_router(agent_runtime.router, prefix="/api/agent", tags=["agent"])
app.include_router(agent_jobs.router, prefix="/api/agent", tags=["agent-jobs"])
```

创建 Job 的 API：

```text
POST /api/agent/chat_jobs
```

请求必须包含：

```text
prompt
session_id
```

可选：

```text
max_turns
idempotency_key
Idempotency-Key header
```

返回：

```json
{
  "job_id": "...",
  "status": "queued",
  "queue_key": "...",
  "estimated_cost": 2,
  "status_url": "/api/agent/chat_jobs/{job_id}",
  "events_url": "/api/agent/chat_jobs/{job_id}/events"
}
```

## 权限和身份如何进入 Agent

`create_chat_job()` 从 `Principal` 中取：

```text
tenant_id
user_id
role_ids
data_scope
allowed_tools
```

然后传给：

```text
AgentJobService.create_job(...)
```

这一步非常关键。Agent Runtime 后面不会相信模型自己说的权限，而是使用后端快照的身份和数据范围。

## 后端到 Runtime 怎么调用

后端 worker 执行 job 时会走 proxy：

```text
AgentJobService._execute_proxy_blocking()
-> POST {agent_base_url}/api/chat_stream
```

其中 `agent_base_url` 默认：

```text
http://127.0.0.1:7862
```

可通过环境变量覆盖：

```text
CLAWD_AGENT_WEB_URL
AGENT_WEB_BASE_URL
```

## 面试官可能怎么问

### 问：前端是直接调用大模型吗？

30 秒回答：

> 不是。前端调用后端 `POST /api/agent/chat_jobs` 创建异步 Agent Job，后端负责身份快照、路由估价、排队调度和 Runtime 调用。前端再通过 `events_url` 订阅 SSE 获取执行过程和最终结果。

2 分钟展开：

> 这样设计是因为 Agent 任务不是普通短请求。它可能涉及多轮模型调用、RAG、SQL、图表、PPT 和失败恢复。做成 Job 后可以支持排队、限流、会话锁、取消、重试、断线续传和审计。后端还会把用户的 tenant、role、data_scope、allowed_tools 固化到 job 里，保证 Runtime 执行时有权限边界。

源码级追问：

> 入口在 `backend/app/routers/agent_jobs.py` 的 `create_chat_job()`。它调用 `get_agent_job_service().create_job()`，返回 job_id、status_url 和 events_url。后端真正执行时在 `AgentJobService._execute_proxy_blocking()` 里请求 Runtime 的 `/api/chat_stream`。

### 问：为什么不用一个同步接口？

30 秒回答：

> Agent 任务耗时不可控，可能多轮工具调用。异步 Job 更适合做排队、取消、恢复、SSE 过程展示和失败审计。

继续追问：

> 如果同步请求中途断开，任务状态和工具结果很难管理。Job 化后，任务状态、事件、final metadata 都能持久化，前端断线后还可以根据 job_id 恢复。

### 问：session_id 有什么用？

30 秒回答：

> session_id 用于会话隔离和会话锁。同一个 session 同时只允许一个 job 执行，避免多个 Agent 并发写同一段对话状态。

## 容易踩坑

- 不要说“前端直接调 Agent Runtime”。真实链路是前端 -> 后端 Job -> Runtime。
- 不要忽略权限快照，面试官会追问数据安全。
- 不要把 SSE 和 Runtime streaming 混为一谈：前端订阅的是后端 job events。

## 本层小结

全栈链路是项目从 demo 到应用的第一层差异。Agent Loop 在 Runtime 内部，但用户请求必须经过后端 Job 系统才能安全、可控、可恢复地执行。
